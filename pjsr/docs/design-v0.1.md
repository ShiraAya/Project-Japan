# PJR × SR 日本路网自动生成初步方案

> **方案版本：** v0.1（初步设计稿）  
> **日期：** 2026-10-20  
> **适用项目：** ProjectJapanRefined（PJR）、SplineRoads（SR）；后续可联动 Project Japan Map（PJM）  
> **比例基准：** X : Y : Z = **0.5 : 0.5 : 0.5**  
> **核心目标：** 在 PJR 世界生成过程中，通过 SR 自动生成日本真实的高速公路与国道骨架，其他道路留给玩家建设。

**文档性质：** 本文整理已确定的产品方向，并提出实现架构、边界处理和验收建议。它不是已实现功能说明，也不是对最新 PJR、SR 源码完成联合核验后的接口报告。文中的模块名、数据结构名和状态名均为建议命名，不代表现有代码已经具备相应能力。

---

## 1. 目标与设计基线

### 1.1 已确定的方向

| 项目 | 设计基线 |
| --- | --- |
| 世界比例 | PJR 三轴统一为 0.5，不能继续使用早期的 0.375 |
| 生成方式 | 道路像河流一样，随新区块生成自然出现，不要求玩家选择区域后手动批量施工 |
| 自动生成范围 | 高速公路与国道，以及维持这些道路连接所必需的匝道、路口和桥隧结构 |
| 不自动生成的范围 | 都道府县道、市町村道路、住宅区道路及其他普通地方路网，留给玩家自由发挥 |
| 地形基础 | 使用 PJR 的地形、水系和地理坐标体系 |
| 道路实现 | 复用 SR 的道路几何、碰撞、标线、桥隧和编辑能力，避免另写一套互不兼容的道路系统 |
| 玩家建设空间 | 自动道路提供交通骨架，而不是填满所有街区 |

0.5 的比例与精简后的道路范围，可以作为本方案的实施基线。**不把再次放大世界、全面缩小 SR 道路，或默认删除大量高速与国道作为前置条件。** 局部复杂立交、并行道路和窄谷仍需通过实际数据验证，不能仅凭比例宣布所有位置都不会冲突。

### 1.2 建议沿用的项目原则

游戏运行保持离线；SR 继续作为可独立使用的 Mod；自动生成道路应允许玩家后续编辑；优先保证连通、可通行、性能和存档安全，再补齐装饰设施。

本方案中的道路宽度按 SR 的实际建造尺度适配，不随地理坐标机械缩为一半。自动生成道路建议统一采用左侧通行配置，但不得因此修改其他世界或玩家已有道路的行驶方向。

## 2. 生成范围与边界

### 2.1 纳入的内容

| 内容 | 处理原则 |
| --- | --- |
| 高速公路主线、都市高速 | 保留实际路线、方向及上下行关系 |
| 一般国道 | 保留当前纳入数据快照的现役机动车通行路段，不统一扩成四车道 |
| 国道汽车专用路段 | 按高速型道路结构处理，仍记录其国道身份 |
| 高速之间的连接匝道（JCT） | 属于骨干路网的一部分，需要保留连接关系 |
| 高速出入口（IC） | 生成目标高速的必要匝道；与未纳入的地方道路相接时采用接建接口方案 |
| 国道之间、国道与高速之间的连接 | 按实际平交、分流、汇流或立体交叉关系处理 |
| 桥梁、高架、隧道 | 是维持骨干路网可通行性的必要结构，不应全部拖到装饰阶段 |

“高速”不能仅等同于一个 OSM 标签。日本 OSM 的 `motorway` 范围包含汽车专用道路，不完全等同于法律分类上的高速公路；`trunk` 通常对应非汽车专用的一般国道。它们应作为候选入口，再通过路线身份和人工例外规则确定最终范围。[^osm-jp]

### 2.2 明确不纳入首版的内容

地方道路网络、街区道路、停车场道路、服务区内部道路、铁路、建筑及完整城市规划不属于本项目的首版目标。收费站建筑、服务区建筑、复杂路牌和密集照明也不应成为基础路网能否交付的前置条件。

国道路线关系中的渡轮、台阶、步道，以及规划中、未建成、废弃等不符合现役机动车道路目标的部分，不得为了让线路“看起来连续”而生成虚构公路。应保留明确的非道路区段或数据问题记录，不能跨海、穿山强行补线。路线关系本身并不保证所有成员都是可驾车道路。[^osm-jp-en]

### 2.3 高速出口连接地方道路时怎么办

采用 **“保留高速出口，停止扩展地方路网，提供玩家接建接口”** 的建议规则：

1. 保留属于目标高速的出入口匝道，生成至与地方道路交接的合理位置。
2. 该位置只保留必要的匝道收口、结构和可识别端点，不顺着地方道路继续生成街区。
3. 如果省略地方道路后没有实际平交需求，不凭空生成四岔路口、停止线和整套信号灯。
4. 接口必须有可站立路面、合理收口和 SR 可连接的方向信息，不能以悬空断面或护栏封死接口交付。
5. 若实际连接点处于高架等特殊结构，需单独规划可接建接口；不能随意把它降到地面来伪装已经解决。

普通国道与未生成地方道路的交叉点，默认保持国道主线连续；不批量留下空路口。玩家需要接入时，再使用 SR 创建或修改路口。

这类接口只是保留高速自身功能的边界处理，**不是允许自动生成地方道路网络的例外入口。**

## 3. PJR、SR 与适配层的分工

### 3.1 总体架构

```text
开发阶段：真实道路原始数据
    ↓ 筛选、拓扑清洗、属性整理、坐标转换、版本固化
离线路网资源包
    ↓
PJR：提供地形、水系、坐标转换与区块生成入口
    ↓
PJR—SR 适配层：道路规划、地形协调、空间索引、生成状态
    ↓
SR：生成道路几何、路面、碰撞、标线、必要结构及编辑对象
    ↓
新区块中的可使用道路 + 可持久化、可编辑的道路记录
```

上述为职责划分，不要求将适配层做成第三个必须安装的 Mod。初期可放在 PJR 的独立兼容模块中，SR 则提供边界明确的生成接口。

### 3.2 职责表

| 模块 | 主要负责 | 不应负责 |
| --- | --- | --- |
| PJR | 地理坐标、基础地形、水文结果、世界生成接入、资源版本约束 | 重写 SR 的完整路面和匝道渲染器 |
| 离线编译工具 | 筛选高速与国道、整理拓扑、压缩资源、输出问题清单 | 在玩家游戏过程中下载全国数据 |
| 适配层 | 真实路网转 SR 道路描述、纵断面协调、跨区块一致性、来源与覆盖记录 | 模拟玩家点击工具、反复调用预览或交互式整路施工 |
| SR | 统一道路几何与碰撞、标线、桥隧等结构、编辑和删除等操作 | 自行推断日本国道身份、维护另一套 PJR 地理投影 |
| PJM（后续） | 读取统一路网及玩家改动，展示道路 | 另起一套位置不一致的道路采样与生成逻辑 |

### 3.3 安装与兼容建议

PJR 单独安装时仍可生成原有地形与水系；只有 SR 和兼容版本的道路资源齐备时，才能创建启用道路的世界。创建时缺少依赖，应明确提示，而不是悄悄生成一个缺路世界。

已经启用道路的存档，不能在卸载 SR、缺失资源包或接口不兼容时静默退化。应给出明确的缺失依赖提示，避免继续保存造成道路方块、数据或接口记录损坏。

## 4. 数据来源、筛选与离线编译

### 4.1 数据来源

建议以 OSM 为主要路网来源。Geofabrik 提供日本及其子区域的 OSM 提取数据，可作为开发阶段离线编译的输入。玩家运行时只读取编译后的精简资源，不直接读取全国原始 PBF。[^geofabrik]

初版使用固定快照，不追求实时同步现实路网。资源清单必须记录数据日期、来源、内容校验值、编译器版本、坐标体系和筛选规则版本。

官方道路资料可作为后续核验与人工修补的辅助来源，但本方案不预设某个官方数据集必然具有完整拓扑、车道和桥隧高程，也不在未核实许可前把其他地图数据直接混入资源包。

### 4.2 候选识别规则

| 输入信息 | 建议用途 |
| --- | --- |
| `highway=motorway / motorway_link` | 提取汽车专用道路与相关连接路候选，再核实是否属于目标高速或国道范围 |
| `highway=trunk / trunk_link` | 提取一般国道与相关连接路候选 |
| `type=route`、`route=road`、路线编号及路线关系 | 补充道路身份，核查不采用常规分类标签的目标路段 |
| 道路名称、运营或管理信息、人工规则 | 解决候选歧义；名称或编号不能单独作为唯一判据 |
| 使用状态和机动车访问属性 | 排除不符合现役机动车道路目标的路段；正确处理具体车辆权限对通用权限的覆盖 |

以上是方案规则，不是已经对全国数据验证完毕的筛选器。尤其不能只用“存在 `ref`”认定国道，也不能把全部 `motorway` 无条件算作目标高速。对无法确认的候选，应输出原因和待核查记录。

### 4.3 保留的最小属性

建议保留来源对象 ID、路线身份、原始中心线、方向、道路等级、连接关系、车道信息、桥隧属性、层级、名称与编号，以及每项推断结果的来源和可信度。

车道解析必须遵循字段含义：`lanes` 表示该道路对象的机动车车道总数，不能对双向道路误解为“每个方向的车道数”；方向车道需要结合 `lanes:forward`、`lanes:backward` 等信息。[^lanes] 单行方向还需正确处理 `oneway=-1` 等情况，而不能默认都沿原始点序行驶。[^oneway]

缺失属性允许采用可配置的保守默认值，但必须标记为推断。不能因为数据不足，就把全部国道变成宽阔道路、把全部高速变成同一车道数。

### 4.4 离线编译流程

```text
固定来源快照
→ 筛选高速、国道及其必要连接
→ 保留相关节点、路线关系和必要转向限制
→ 去除非目标道路与不符合条件的区段
→ 整理同路共线、上下行和匝道关系
→ 保留路口/桥隧边界等锚点，简化普通折线
→ 使用 PJR 坐标转换生成地理道路计划
→ 建立空间索引与跨分片引用
→ 输出压缩资源、清单、统计和异常报告
```

同一路段同时属于多个国道编号时，只生成一份道路实体，保留多个路线编号。省界、数据分片边界和 OSM way 分段都不应被误当作实际道路终点。

### 4.5 资源发布方式

初期使用区域测试包；正式发布优先评估一个全国骨干路网包。若实测体积不满足项目的小体积目标，再考虑区域分包。

不预先承诺全国路网能压到某个 MB 数值。应分别统计原始数据、精简路网包、运行时缓存和生成后的存档体积。**空间分片只是存储方式，不应制造道路断点；运行时仍须完全离线。**

## 5. 坐标、尺度与道路宽度

### 5.1 必须复用 PJR 的坐标实现

道路、河湖、地形与 PJM 应调用同一个地理坐标转换来源，包含现行投影、原点、轴向、海平面偏移和高度转换。不得为道路另写一套“近似经纬度换算”，也不得把已缩放数据再乘一次 0.5。

以下为比例换算示例，不代替实际投影代码：

| 现实尺度 | 0.5 比例下的理论尺度 |
| --- | --- |
| 1 km 水平距离 | 500 格 |
| 40 m 道路中心线间距 | 20 格 |
| 2 × 2 km 区域 | 1000 × 1000 格 |
| 6 m 高差 | 3 格 |

投影坐标和道路控制点保留足够精度；不要在提取每个原始点时就整数取整。方块化应尽可能留到最终写入阶段。

### 5.2 路面宽度不机械减半

道路中心线的地理位置按 0.5 比例转换，路面横断面按 SR 的可用尺度生成。主线车道数优先采用可靠数据；标线、护栏、肩部及必要结构则使用经过核验的 SR 规则。

道路宽度与地理缩放属于两种不同尺度。因此，0.5 比例虽比早期方案提供更多空间，但不能作为自动忽略局部碰撞检查的理由。

### 5.3 局部拥挤的处理顺序

首先核查是否重复生成、是否把上下行道路重复扩成双向道路、是否把立体交叉误判成平交。排除数据与逻辑问题后，再缩减非必要装饰、调整路肩或允许有上限的小幅位置修正。

不得未经记录就删除目标主线、减少可靠的主线车道、合并不同层级道路，或大范围偏移真实路线。仍无法解决时，输出局部修补任务，不能用任意拉直或穿模代替处理。

## 6. 路网拓扑与几何生成

### 6.1 先确定连接，再拟合曲线

道路不能简单理解为“每个 OSM way 生成一条独立的 SR 道路”。需要先建立路段—节点图，识别真实路口、匝道汇入汇出、车道变化、上下行关系与桥隧边界，再生成可供 SR 使用的几何描述。

道路的数学曲线可以跨多个区块，但编辑对象应划分为长度可控、具有稳定来源映射的单元，避免玩家修改一个路口就触发整条跨地区国道重建。

### 6.2 三条关键规则

**二维交叉不等于路口。** 不能因为两条中心线在地图上相交就自动连通，应结合共享节点、道路语义、桥隧和层级判断；可疑矛盾进入诊断报告。

**近邻道路不等于同一条路。** 分离式上下行、并行国道、辅线及不同层级道路不能按距离直接合并。确有必要合并为一个 SR 横断面时，必须证明方向、层级和连接关系兼容。

**平滑不得改变连接。** 路口、匝道口、桥隧出入口与属性变化点作为锚点保留；只在允许的误差和避障范围内简化普通折线，不能把发卡弯平滑成穿山直线。

### 6.3 立交生成策略

优先依据真实主线与匝道中心线逐条重建，再调用 SR 的匝道、合流、分流及桥隧能力。只有布局和连接关系明确匹配时，才使用完整的三向、四向等立交模板。

复用 SR 的目的在于复用稳定的几何与结构能力，而不是把所有现实立交改造成有限几种模板。不能为了套模板而增加、删除或反转实际交通连接。

## 7. 高程、地形与水系协同

### 7.1 道路高程的来源

纵断面应综合 PJR 的最终基础地形、水系结果、道路桥隧属性、可靠高程信息及 SR 的通行约束求解。这里的“最终基础地形”指尚未被当前道路和玩家建设修改的可重复采样结果。

OSM 的 `layer` 表达相交对象的上下关系，并不提供真实高度差。**不得使用“`layer=1` 就固定抬高若干格”的全国统一算法。**[^layer] `bridge`、`tunnel` 可提供结构语义，但同样不能被当成完整桥面或隧道路面高程。[^bridge][^tunnel]

### 7.2 地形与净空约束

地面道路采用有限范围整平、局部挖填及边坡过渡；桥梁在不堵塞水道、不过度填平谷地的前提下跨越；隧道只开挖所需通行空间，并处理洞口、顶部覆土及防漏水。

三轴等比缩放本身不会改变理想坡度，因为高差与水平距离同时减半。但是 SR 的路面厚度、通行净空并不机械减半；为满足这些条件而重新调整桥面高度后，仍需要重算引道与匝道坡度。

净空、坡度、最小曲线和结构厚度应复用经核验的 SR 配置，不在本方案中另行硬编码一组未经验证的全国参数。净空检查必须考虑下层通行空间与上层梁底，而不只是两条中心线的 Y 差。

### 7.3 水系保护

PJR 的河床、水面及湖岸规划应先提供可查询约束，道路规划再决定桥梁、引道和洞口位置。道路不得通过填满河道、截断汇流、覆盖湖口、整体抬高水面等方式解决冲突。

桥墩应检查与河道及其他道路的冲突；隧道应检查水体和地表穿透风险。来源道路与现有 PJR 地形明显不一致时，应定位数据或坐标问题，不得无限加高桥墩或大范围削山。

### 7.4 无法自动解决时

按“修正数据 → 有限几何调整 → 匹配的桥隧处理 → 局部人工修补”处理。无法满足约束的区域应明确标记并阻止被报告为验收通过。

测试阶段可以局部停用失败的结构并输出原因；正式数据包中的目标道路断口则必须修复，或明确标注为真实非道路区段/已知限制，不能静默跳过后宣称全国路网完整。

## 8. 像河流一样接入世界生成

### 8.1 原则：整体规划，局部落地

**同一条道路的中心线、纵断面和连接关系必须来自一致的计划；每个区块只生成属于自己的那部分。**

不能等某个区块加载后，才根据它当前能看见的邻块临时决定道路高度、走向或立交形式。否则探索方向不同，就可能得到不同结果。

离线阶段固化范围、拓扑、平面路线及约束。与世界种子、地形版本相关的纵断面，可在运行时通过 PJR 的纯采样能力进行确定性规划并缓存；前提是无需强制加载沿线区块，且不同区域对共享锚点采用一致规则。若当前 PJR 缺少这样的查询能力，应先补齐接口，而不是改用已加载区块的实时地表凑合。

### 8.2 建议生成顺序

| 顺序 | 工作 |
| --- | --- |
| 1 | 从资源索引查询当前区块及必要规划边界内的道路、水系与结构约束 |
| 2 | 获取一致的道路计划及纵断面；计算桥隧、路口和道路占用范围 |
| 3 | 在 PJR 基础地形与水文结果上应用受限的路基挖填或隧道开挖 |
| 4 | 通过 SR 的数据驱动接口，输出当前区块内的路面、碰撞、标线和必要结构 |
| 5 | 按道路占用范围避让植被等后续生成内容，避免树木长进路面和隧道净空 |
| 6 | 持久化当前区块完成状态及道路来源记录，供运行期注册和编辑使用 |

这里描述的是逻辑顺序，具体接入哪个世界生成阶段，需要结合实际版本源码确定。不得直接把需要完整运行世界、玩家对象或主线程全局状态的 SR 交互式施工入口塞进区块生成回调。

### 8.3 跨区块与跨分片一致性

道路的采样基准、标线相位、护栏分段和桥墩布置，应以整条编辑单元的稳定里程和锚点为准，不能在每个区块重新从零开始。

一个路口或立交只有一份整体计划；其路面、结构和附属物再按区块裁切。不能让相邻四个区块各自生成一座完整路口。

每个方块或生成片段必须有明确归属，同一项写入可重试但不能重复叠加。不能依赖“起点所在区块必须先生成”，也不能为生成一座立交强制加载沿线所有未探索区块。

涉及共享运行时数据的注册，应与纯几何计算分开，并在适合的线程和生命周期中完成。服务端道路数据与区块写入之间要有可恢复记录，避免崩溃后只剩路面却无法编辑，或只有记录却没有实际道路。

## 9. SR 接口与运行期道路对象

### 9.1 建议的接口边界

建议划分四类能力，具体方法签名在源码审查后确定：

| 能力 | 输入/输出意图 |
| --- | --- |
| 道路规划描述 | 输入控制点、横断面、行驶方向、连接和结构约束；输出可重复计算的道路计划 |
| 当前区块片段生成 | 输入整体计划与当前区块范围；输出本区块的几何、结构或方块补丁 |
| 运行期登记与查询 | 以稳定道路 ID 登记或恢复编辑对象，按空间索引查询 |
| 玩家修改回传 | 将编辑、删除、分割和连接结果写回覆盖记录及依赖关系 |

适配层不应复制 SR 的整套道路渲染器、路口标线和碰撞实现。若原接口有大量交互式副作用，应先抽取可复用核心，再接世界生成。

### 9.2 自动道路也是可编辑道路

自动生成结果不应仅是一层与 SR 无关的沥青方块，也不应为了可编辑而沿每条长路放置大量可见端点。建议使用可持久化的逻辑端点和道路描述，在玩家持有相关工具或编辑时按 SR 原有交互显示。

道路表面、碰撞与渲染必须有唯一归属，避免同时被地形和独立网格重复绘制，造成闪烁、双层路面或删除后残影。

SR 当前支持的道路编辑、删除、分割与接建操作，应逐项验证自动道路兼容性。仍存在的立交、匝道和过渡段保护限制应保留，不能为了让工具“可用”而关闭安全检查。

### 9.3 附属设施

初版优先路面、标线、必要护栏和桥隧结构。路灯、复杂龙门架、标牌、收费站等建议分级启用，不默认在全国沿线密集生成。

如后续接入收费站，应沿用“独立收费站设施提供道路接口，再连接道路”的设计；不要为了自动道路另创一套直接覆盖既有路面的收费站机制。道路名称显示沿用项目命名原则：有可靠中文译名时采用，无可靠译名时保留日语原名。

## 10. 持久化、玩家改动与升级

### 10.1 推荐数据分层

```text
不可变基础层：资源包中的道路计划与来源关系
        +
生成状态层：各区块/结构片段的完成状态、版本和恢复记录
        +
玩家覆盖层：修改、删除、分割、新连接及其影响范围
        =
当前世界中实际有效的路网
```

道路 ID、区块 ID 和 SR 编辑对象 ID 需要分别管理，并保留映射。不能把 OSM way ID 直接等同于永久不变的整条道路身份，也不能用随机生成的新 UUID 使每次加载都产生另一条路。

### 10.2 玩家改动优先

| 操作 | 必须保持的结果 |
| --- | --- |
| 编辑道路 | 保存新的设置与几何；再次加载不以基础计划覆盖 |
| 删除整条编辑单元 | 保存删除记录，阻止未生成邻块在未来重新补出该单元 |
| 只删除或分割一部分 | 记录准确区间及子对象来源，不误删整条跨地区路线 |
| 新建连接或路口 | 保存与原路的依赖和车道关系，后续生成邻块也采用修改后的边界 |
| 普通破坏方块 | 不通过周期性“自愈”扫描自动补回；需要明确维护行为时另做显式工具 |
| 卸载后重载、退出后进入 | 结果保持，不恢复为最初自动生成状态 |

建议使用类似 `AUTO / PLAYER_OVERRIDDEN / DELETED` 的语义区分自动计划与玩家覆盖，但实际状态机还需覆盖部分生成、失败恢复和分割继承。

跨未探索区域的编辑，应先确定修改影响的逻辑范围，再由后续区块生成读取同一份覆盖结果。不能只修改当前已加载的半条道路，让另一半未来按旧计划重生。

### 10.3 世界版本锁定

创建世界时保存道路资源快照标识、生成规则版本、PJR 坐标/地形版本及 SR 兼容配置。更新 Mod 或下载新数据，不应静默改变同一存档后续新区块的道路位置和高程。

旧世界默认不追溯铺路。未来如需补建，必须设计为显式、可预览且带保护范围的独立迁移操作；不属于首版自动生成机制。

道路开关、资源替换与生成规则更新应有明确兼容策略，不允许简单切换后在已探索与未探索区域之间制造无法连接的断层。

## 11. 性能与体积控制

### 11.1 不把全国路网变成运行期全局活跃对象

全国道路采用分片资源和空间索引，运行时只加载必要区域及其依赖。路面几何、碰撞索引、客户端网格和编辑记录均应有空间边界与缓存回收策略。

不能让每帧渲染、每次道路编辑或每个服务器 tick 都遍历全国道路。客户端只接收视野和交互需要的道路数据；离开区域后允许缓存回收，不能把“一次探索过”解释为“永久驻留内存”。

### 11.2 生成任务必须有边界

世界生成只查询命中当前区域的道路，复用已完成的计划，不在运行时扫描原始 PBF、联网请求道路或执行无上限的全局避障搜索。

规划单元、依赖范围、重试次数、缓存容量和任务队列应设定上限；具体数值由样例实测确定。达到边界时记录明确失败原因，不能让一个异常立交拖住无限数量的区块任务。

### 11.3 Infill 与地形回填

结合项目此前的性能反馈，自动生成道路模式应重点避免大量细碎 `RoadInfill` 几何：路基能由普通完整地形方块表达时，优先使用完整方块；保留必要的 SR 平滑路面，不把道路简单退化成阶梯。

禁止为了贴合边缘、斜坡或匝道空隙，无上限地产生薄片填充结构。完整方块数量、不可见面、结构重叠和渲染批次也需统计，不能把“没有薄片”视为性能已经解决。

### 11.4 基准测试要求

至少分别测试：PJR 无道路、普通国道、桥隧路段、高速主线、完整立交，以及长距离探索后的往返场景。记录区块生成耗时分布、服务端 tick、客户端帧时间、内存、道路对象数、网格量和存档增量。

实际支持的 VBO、terrain 及光影组合应分别验证。比较时固定硬件、视距、画质和路线；不预先承诺某个 FPS，也不以总平均值掩盖高速移动时的卡顿峰值。

## 12. PJM 联动（后续阶段）

PJM 应读取与世界生成相同的道路坐标和身份数据，避免地图路线与实际路面错位。玩家修改、删除、新建连接后，通过同一份覆盖记录更新地图结果。

需要区分“资源包中规划存在的道路”和“当前存档已经生成、实际有效的道路”。地图是否显示未探索区域的规划道路，可作为后续选项；默认表现不应把尚未生成或已删除的路线误标成实际建成道路。

PJM 是展示消费者，不应承担道路生成任务，也不应反过来成为 PJR 道路世界生成的必需依赖。

## 13. 分阶段实施

### P0：接口核验与最小闭环

**目标：证明道路能够随区块生成，并作为 SR 道路保存和编辑。**

先核对实际 PJR 的 0.5 坐标实现、地形/水系采样方式，以及 SR 的道路数据、几何、碰撞、持久化和线程限制。使用极小的固定路网样例，验证道路跨区块生成、相邻区块不同顺序生成、退出重进和玩家删除后的行为。

样例可先用人工构造的道路计划测试接口，但必须标明是工程测试数据，不作为真实日本路网成果。通过后接入一个真实小区域。

**出口条件：** 有完整的生成—保存—加载—编辑闭环；无强制沿路加载区块；SR 的手动建造与原有世界不受影响。

### P1：真实国道试验区

**目标：完成真实国道、基础路口及必要地形适配。**

建议选择约现实 2 × 2 km 的主体展示区，在当前比例下约为 1000 × 1000 格；编译与规划必须保留外围缓冲范围，不能将裁剪边界误认为道路终点。样本应覆盖直线、弯道、国道相交、跨区块和至少一处必要桥梁；不足的结构类型另设独立样例。

完成数据筛选、坐标验证、基础车道、左侧通行、路基与桥梁、SR 编辑兼容及诊断输出。遇到尚不支持的必要结构，应明确限制试验区，而不是删掉该段后宣称道路完整。

**出口条件：** 试验区目标路线可连续使用；路口关系正确；河流未被截断；没有区块缝隙和重复生成；玩家改动能够持久保存。

### P2：高速、匝道、立交与完整桥隧

**目标：还原目标高速路网的实际连接关系。**

加入分离式上下行、高速出入口、JCT、国道连接匝道、复杂纵断面及隧道，并落实地方道路接口边界。以真实路网重建为主，模板匹配为辅。

**出口条件：** 匝道方向、车道连接和上下层关系正确；满足 SR 的通行与结构约束；没有强行套模板、穿模或无解释断口；玩家可接建地方道路。

### P3：全国数据、优化与地图联动

**目标：在离线、可控性能和可升级的前提下推广至全国目标路网。**

完成全国候选筛选与覆盖统计、异常修补、分片压缩、长期探索性能验证、多人服务器验证、资源版本管理及 PJM 联动。

全国覆盖应同时报告纳入、排除、推断和待修复的路段及原因，不只给出一个“道路总数”。来源本身的非道路区段、缺失数据和程序生成失败必须区分统计。

## 14. 验收清单

| 类别 | 必测内容 | 通过标准 |
| --- | --- | --- |
| 比例与定位 | 与 PJR 地形、水系及已知坐标对照 | 使用同一转换，无重复缩放和系统性偏移 |
| 范围 | 高速、国道、地方道路交界 | 仅生成目标骨架，地方路网没有被自动展开 |
| 拓扑 | 平交、立交、上下行、同路多编号 | 无错误连接、方向反转或重复路面 |
| 边界 | 区块角点、资源分片、省界、裁剪窗口 | 不因存储或生成边界产生断路 |
| 确定性 | 改变探索顺序、并行生成、重复加载 | 在相同版本、种子和配置下，生成结果一致 |
| 结构 | 桥梁、隧道、匝道、路口 | 净空、碰撞、护栏和路面连续，必要结构不缺失 |
| 水文 | 跨河、湖岸、入出湖口 | 不填断水道，不为道路修改整体水位 |
| 编辑 | 修改、删除、分割、接建、跨未探索区段 | 覆盖记录有效；重载和后续生成均不恢复旧路 |
| 崩溃恢复 | 写入中断、登记中断后恢复 | 不重复创建，不留下永久不可编辑的孤立道路 |
| 性能 | 长距离探索、立交集中区、区域往返 | 有可复现数据，缓存可回收，无全国逐帧扫描 |
| 兼容 | 单机、专用服务器、多人及支持的渲染模式 | 无客户端类误用、重复施工和不同步 |
| 升级 | 更新 Mod、替换资源、缺失依赖、旧存档 | 有明确策略，不静默覆盖或造成新旧道路断层 |

几何接缝、净空和错误连接等硬性错误，应逐项修复或标为未通过。性能门槛需在 P0/P1 建立基线后确定，不能用未经实测的数字作为已达到的指标。

## 15. 主要风险与待核验项

| 风险/待核验项 | 对应措施 |
| --- | --- |
| 现有 SR 创建流程依赖玩家、完整区块或主线程副作用 | P0 先拆分纯规划、局部写入与运行期登记，不直接复用工具点击入口 |
| PJR 最终水文地形不能在区块外稳定采样 | 补充可重复的查询接口或采用与世界版本一致的预计算约束 |
| 数据属性不足、身份歧义、缺失连接 | 记录可信度、提供有边界的默认值和人工修补清单 |
| 0.5 比例下局部道路与结构仍发生冲突 | 优先排除重复与拓扑错误，再做有限调整；不默认删主干道 |
| 复杂立交不能被现有 SR 模型表达 | 扩展必要的数据驱动几何能力，或将该结构列为明确阻塞项 |
| 玩家修改与未生成区块产生冲突 | 对逻辑区间保存覆盖和删除记录，生成时先查询覆盖层 |
| 全国活跃道路对象、Infill 或缓存导致性能回退 | 空间分片、按需激活、有界缓存、网格与方块预算、实测验收 |
| 版本更新造成断路和数据损坏 | 锁定世界快照与规则版本，迁移另行设计 |

开发前必须核验的入口包括：实际 PJR/SR 基线版本、投影实现、世界生成阶段、SR 道路身份与持久化结构、局部几何生成能力、各编辑工具适用范围，以及客户端/服务端边界。本方案不指定未经查看的现有类名或声称某个接口已经可直接调用。

## 16. 数据许可与来源记录

OSM 数据使用 ODbL；公开分发数据或由其派生的内容，需要按适用条款处理署名、许可说明及衍生数据库义务，不能仅写“开源数据”就视为完成合规。具体发布物是数据库、衍生数据库还是作品，应结合最终分发形式核实。[^osm-license]

建议将路网资源、来源清单、校验值和许可文件单独组织，并在游戏菜单或适当的署名位置说明 OpenStreetMap 来源。OSMF 的署名指引对游戏和模拟程序提供了具体展示方式。[^osm-attribution]

数据许可与 PJR/SR 代码许可分别管理，不应简单推断“用了 OSM 就必须把全部 Mod 代码改成 ODbL”，也不能用代码许可覆盖第三方地理数据的许可义务。

---

## 17. 交给开发阶段的第一项任务

**先完成一个跨区块、可保存、可编辑的真实小区域原型，不直接启动全国铺路。**

第一批交付应包含：实际源码接口核验记录、最小离线路网资源、PJR—SR 接入实现、生成与覆盖记录、可重复测试方法，以及已通过/未通过项目清单。

在这个原型中，必须同时证明：道路能随新区块出现，边界不断裂，重新进入不重复，玩家删除不重生，国道不会因地方道路缺省而生成大量空路口。随后再扩大国道覆盖、加入高速立交，最后推广到全国。

**最终定位：PJR 提供真实日本的地理与交通骨架，SR 将骨架生成可使用、可编辑的道路，骨架以外的城市与地方路网仍由玩家自由建设。**
